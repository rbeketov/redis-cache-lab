# Как сдать работу

Задание и приём работ находятся в [rbeketov/redis-cache-lab](https://github.com/rbeketov/redis-cache-lab). Сдача состоит из кода, заполненного отчёта и ссылки на видеоролик. Всё объединяется в **одном Pull Request (PR) в ветку `main` репозитория автора**.

| Что сдавать | Куда загружать |
|---|---|
| Реализацию и собственные тесты | В рабочую ветку своего fork, затем в PR автору |
| Отчёт | Файл `REPORT.md` в той же ветке |
| Результаты проверок | В `REPORT.md` и кратко в описание PR |
| Видео до четырёх минут | В хранилище или видеохостинг с доступом по ссылке |
| Ссылку на видео и длительность | В описание PR и раздел «Видео» отчёта |

Код обязателен. Одна ссылка на видео без проверяемой реализации не является полной сдачей. Не добавляйте сам ролик, `.venv`, кэш pytest и личные настройки в Git.

## Шаг 1. Создать fork и ветку

Если вы уже выполнили этот шаг по README, переходите к шагу 2.

1. Войдите в GitHub и откройте [форму создания fork](https://github.com/rbeketov/redis-cache-lab/fork).
2. Выберите свой аккаунт в Owner, оставьте имя `redis-cache-lab`, нажмите **Create fork**.
3. В терминале bash/zsh/WSL замените `your-github-login` своим логином и выполните:

```sh
GITHUB_USER=your-github-login
git clone "https://github.com/$GITHUB_USER/redis-cache-lab.git"
cd redis-cache-lab
git remote add upstream https://github.com/rbeketov/redis-cache-lab.git
git switch -c solution/redis-cache
git remote -v
```

Проверьте: `origin` относится к вашему аккаунту, `upstream` — к `rbeketov`. Если выбрали другое имя fork, скопируйте его URL через **Code** и используйте его в `git clone`. Для Windows рекомендуется терминал WSL или Git Bash.

## Шаг 2. Выполнить задание и проверки

Выполняйте [этапы задания](ASSIGNMENT.md) по порядку. Основная реализация находится в `app/service.py`. Можно добавлять вспомогательные модули. Заполните `REPORT.md` реальными результатами и объяснениями.

Из корня своей копии запустите окружение:

```sh
docker compose up --build -d api
```

Для Б и Б+:

```sh
docker compose run --rm tests python -m pytest -q -m 'smoke or basic'
```

Для П:

```sh
docker compose run --rm tests python -m pytest -q -m 'smoke or basic or advanced'
```

Для Э:

```sh
docker compose run --rm tests
```

Для Б+ и выше добавьте собственный тест нового сценария и выполните его отдельно, например `docker compose run --rm tests python -m pytest -q tests/test_my_scenario.py`, подставив настоящее имя своего файла. Не меняйте исходные тесты ради зелёного результата. Если что-то не выполнено, перечислите это в отчёте и PR.

## Шаг 3. Записать и разместить видео

Запишите экран с читаемым кодом и результатами команд, добавьте голосовое пояснение. Общая длительность — не более **4:00**. Рекомендуемый сценарий на 3:40:

| Время | Что показать |
|---|---|
| 0:00–0:40 | `service.py`: путь чтения, TTL, инвалидация, обработка ошибки Redis |
| 0:40–1:40 | Повторный GET, изменение `source_reads`, PATCH и новая цена |
| 1:40–2:45 | Проверки заявленного уровня и один характерный сценарий сбоя или конкурентности |
| 2:45–3:40 | Выполненные этапы, ограничения и объяснение дополнительного механизма для П/Э |

Для П покажите число обращений к источнику при 20 конкурентных запросах. Для Э покажите stale-ответ и последующее обновление либо соответствующий детерминированный тест. Установку зависимостей и долгую сборку в ролик включать не нужно. Код должен быть показан хотя бы кратко.

Разместите ролик одним из способов:

- **Яндекс.Диск или Google Drive:** загрузите видео, включите просмотр для пользователей со ссылкой и скопируйте ссылку на файл.
- **Видеохостинг:** загрузите видео с режимом доступа по ссылке и скопируйте ссылку на просмотр.

Проверьте ссылку в приватном окне браузера: эксперт должен иметь возможность просмотреть или скачать файл без запроса разрешения у вас. Вставьте ссылку и длительность в `REPORT.md`. Если меняете видео после замечаний, обновите обе ссылки: в отчёте и PR. Отдельная форма для загрузки видео не требуется.

## Шаг 4. Загрузить код и отчёт в свой fork

Просмотрите изменённые файлы:

```sh
git status --short
git diff
```

Для обычного решения достаточно добавить реализацию, собственные тесты и отчёт:

```sh
git add app tests REPORT.md
git diff --cached --stat
git commit -m "Complete Redis caching assignment"
git push -u origin solution/redis-cache
git rev-parse HEAD
```

Если меняли другие файлы по существу решения, добавьте их отдельной командой `git add` и объясните изменения в PR. Сохраните выведенный hash коммита: он должен соответствовать показанной в видео реализации.

При запросе аутентификации используйте свой настроенный GitHub credential manager, token или SSH. Обычный пароль GitHub не используется как пароль для HTTPS push. У вас должны быть права на **свой fork**; права записи в репозиторий автора не нужны.

## Шаг 5. Открыть Pull Request автору

1. Откройте [страницу сравнения](https://github.com/rbeketov/redis-cache-lab/compare) и нажмите **compare across forks**, если GitHub ещё не показывает вашу ветку.
2. Выберите **base repository: `rbeketov/redis-cache-lab`**, **base: `main`**.
3. Выберите **head repository: ваш fork**, **compare: `solution/redis-cache`**.
4. Убедитесь, что в diff только ваше решение, тесты и отчёт. Нажмите **Create pull request**.
5. Название оформите, например: `Решение: GitHub-логин — уровень П`.
6. Заполните автоматически подставленный шаблон. Если он не появился, скопируйте [pull_request_template.md](../.github/pull_request_template.md).
7. Укажите автора/группу, заявленный уровень, сделанное и несделанное, ссылку на видео, длительность, hash коммита, ссылку на отчёт и команды проверки. Ссылку на отчёт скопируйте из своего fork, предварительно выбрав рабочую ветку.
8. Опубликуйте обычный PR. Если работа была Draft, нажмите **Ready for review**, когда она готова к проверке.

**Ссылка вида `https://github.com/rbeketov/redis-cache-lab/pull/…` — итоговая ссылка на сдачу.** Код будет доступен во вкладке Files changed, ролик — по ссылке в описании. Если преподаватель дополнительно собирает ссылки в своей форме, укажите там URL этого PR. Отдельной формы в рамках данного репозитория нет.

Автор проверяет работы по открытым PR. Не нужно самостоятельно сливать решение в `main`: основная ветка остаётся заготовкой для всех студентов.

## Шаг 6. Исправления после обратной связи

Исправляйте ту же ветку, снова запускайте проверки, обновляйте отчёт и делайте новый commit/push. Например:

```sh
git add app tests REPORT.md
git commit -m "Address review feedback"
git push
```

PR обновится автоматически. Если поведение изменилось, обновите ролик, ссылку и hash проверяемой реализации. В ответе на замечание кратко напишите, что исправлено и какой тест это подтверждает. Второй PR для той же работы не нужен, если автор не попросил об этом отдельно.

## Как эксперт получает решение

Для PR с номером 12, из локальной копии репозитория автора:

```sh
git fetch origin pull/12/head:review/pr-12
git switch review/pr-12
docker compose -p review-pr-12 run --build --rm tests python -m pytest -q -m 'smoke or basic'
```

Число 12 — пример; замените его номером проверяемого PR. Для П добавьте `advanced`, для Э выполните весь набор. Для ручного просмотра API: `API_PORT=8012 docker compose -p review-pr-12 up --build -d api`, затем используйте `http://localhost:8012/docs`. Для SWR добавьте `CACHE_MODE=swr` перед командой запуска.

После проверки остановите окружение: `docker compose -p review-pr-12 down`. Все команды одной проверки должны использовать одно и то же имя проекта. При переключении на другой PR сначала остановите API, чтобы bind mount не подхватил чужую ветку.

## Срок и вопросы

Точную дату и время сдачи объявляет автор после согласования с преподавателем. Ориентир курса — 14–16 календарных дней на выполнение, трудоёмкость задания — 10–12 часов. До объявления точной даты этот ориентир не заменяет дедлайн.

Вопросы по постановке и ошибки заготовки можно отправить через [Issues](https://github.com/rbeketov/redis-cache-lab/issues/new). Укажите этап, команду, ожидаемый результат и фактический текст ошибки. Само решение сдаётся через PR.

## Самопроверка перед отправкой

- Код и заполненный отчёт находятся в рабочей ветке, ветка загружена на GitHub.
- PR открыт именно в `rbeketov/redis-cache-lab:main`, а не в `main` своего fork.
- Отчёт и ролик относятся к указанной версии реализации.
- Длительность ролика не превышает 4:00, ссылка доступна для просмотра.
- Команды проверки воспроизводимы, результаты не взяты из чужой работы.
- Указаны выполненные этапы, ограничения и невыполненные части.
