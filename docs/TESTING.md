# Устройство и запуск проверок

Этот документ объясняет, какой код проверяется, в каком окружении и как читать результат. Команды выполняйте в терминале из корня своей копии репозитория, где находится `compose.yaml`.

## Кто запускает проверки

Вы вводите команду вручную. После этого pytest автоматически вызывает операции вашего сервиса и сравнивает их результат с условиями задания. Сохранение файлов и отправка кода на GitHub не запускают тесты. В репозитории нет настроенного GitHub Actions или другого автоматического процесса проверки.

Первый запуск:

```sh
docker compose run --build --rm tests python -m pytest -q -m smoke
```

Compose собирает образ `tests`, запускает Redis, ждёт его готовности и выполняет pytest в отдельном контейнере. После завершения контейнер с тестами удаляется, а Redis остаётся доступным для следующего запуска. Остановить всё окружение можно командой `docker compose down`.

Приложение `api` на порту 8000 для тестов запускать не нужно. Для демонстрации в браузере оно запускается отдельно.

## Какая версия кода используется

Каталог проекта подключается в тестовый контейнер как `/workspace`. Каждый новый запуск pytest импортирует сохранённые файлы из этой папки. Поэтому проверяются и изменения, которые ещё не вошли в commit. Несохранённый текст в редакторе не виден контейнеру.

Образ задаёт версии инструментов: Python 3.12.10 из Dockerfile, Python-библиотеки из `requirements.lock`, Redis 7.4.2 из Compose. Флаг `--build` проверяет актуальность сборки; Docker может повторно использовать неизменившиеся слои. Это нормальное поведение, а не использование старого Python-кода из другой ветки.

Чтобы связать результат с версией работы, выполните:

```sh
git rev-parse HEAD
git status --short
docker compose run --rm tests python --version
docker compose run --rm tests python -m pip freeze
```

В отчёте укажите hash commit и наличие незакоммиченных изменений, команду, результат и сведения об окружении. После изменения зависимостей пересоберите образ. Для сдачи сохраняйте код в commit и проверяйте именно его; видео должно показывать ту же реализацию.

## Что происходит внутри тестов

В `tests/conftest.py` находится общая подготовка — **fixture**. Она создаёт новые объекты источника и вашего `ProductService`, подключает Redis-клиент и после теста очищает созданные им ключи.

- Используется настоящий Redis в контейнере, адрес внутри сети Compose — `redis://redis:6379/0`.
- У каждого тестового экземпляра свой уникальный префикс ключей. Общая база Redis не очищается целиком; демонстрационные ключи API не удаляются.
- Источник в проверках является отдельным объектом. Его счётчики не связаны с `/debug/stats` запущенного API. Тестовая задержка чтения составляет 0,02 секунды, демонстрационная — 0,1 секунды.
- Для проверки истечения срока fixture предоставляет управляемые часы. Тест двигает их без длительного ожидания. Поэтому решение должно использовать переданный `clock()`; реальный TTL Redis дополнительно проверяется отдельной операцией.
- Ошибки Redis имитируются обёрткой над настоящим клиентом: выбранный GET, SET или DEL выбрасывает ошибку соединения. Старый ключ при этом остаётся в Redis. Это воспроизводит важный случай, который не проверяется простым перезапуском пустого Redis.
- Одновременные сценарии используют события ожидания: тест приостанавливает чтение источника и проверяет поведение других запросов. Короткие таймауты обнаруживают зависание, а оценка не зависит от конкретной скорости процессора.
- HTTP-тест создаёт приложение внутри тестового процесса и вызывает его через тестовый клиент. Открытый порт 8000 не используется.

Настройки `CACHE_MODE`, `FRESH_TTL` и `SOURCE_DELAY` в Compose задаются для демонстрационного API. Тесты сами передают свои значения конструктору сервиса. В частности, для группы `expert` не требуется сначала включать SWR через переменную окружения API.

## Группы и ожидаемые результаты

| Группа | Сценарии | Когда должна проходить |
|---|---|---|
| `smoke`, 2 случая | Чтение/изменение источника, API, неизвестный товар, некорректный запрос | Сразу на заготовке и после любых изменений |
| `basic`, 12 случаев | B1: повторное чтение и TTL; B2: истечение; B3: изменение; B4: три ошибки Redis; B5: восстановление; B6: четыре вида повреждения; B7: ошибка источника | После обязательных этапов 1–4 |
| `advanced`, 3 случая | P1: одна загрузка для 20 запросов; P2: независимость ключей; P3: отмена без вечной блокировки | После этапа 5* |
| `expert`, 5 случаев | E1: старое значение и одно обновление; E2: окончательное истечение; E3: изменение во время обновления; E4: ошибка обновления; E5: завершение задач | После этапа 6* |

B1–B7, P1–P3 и E1–E5 — идентификаторы сценариев, а не отдельные оценки. Название каждого теста содержит этот идентификатор. Некоторые функции проверяются с несколькими параметрами, поэтому число случаев больше числа функций.

У неизменённой заготовки `smoke` проходит, а часть остальных проверок падает: кэш ещё не реализован. Некоторые проверки при этом могут уже проходить. Выполнение задания подтверждается всем набором своего уровня и объяснением решения по критериям, а не просто долей зелёных тестов.

## Выбор проверок

Посмотреть полный перечень, не выполняя проверки:

```sh
docker compose run --build --rm tests python -m pytest --collect-only -q
```

В исходном наборе ожидается `22 tests collected`. Собственные тесты увеличат число.

Выбрать группу:

```sh
docker compose run --build --rm tests python -m pytest -q -m basic
```

Проверить обязательную часть вместе с первичными проверками:

```sh
docker compose run --build --rm tests python -m pytest -q -m 'smoke or basic'
```

После её реализации ожидается `14 passed, 8 deselected`. Для П добавьте `or advanced`: ожидается 17 прошедших случаев из исходного набора. Для Э выполните весь набор:

```sh
docker compose run --build --rm tests
```

Выбрать один сценарий по имени и получить подробный вывод:

```sh
docker compose run --build --rm tests python -m pytest -vv tests/test_basic.py::test_b5_recovery_does_not_resurrect_old_price
```

Выбрать несколько сценариев из файла:

```sh
docker compose run --build --rm tests python -m pytest -q tests/test_basic.py -k 'b1_ or b2_ or b6_'
```

`-m` выбирает метку группы, `-k` — фрагменты названий, `-vv` выводит подробности. Имена путей относятся к файлам в корне проекта, подключённым в контейнер.

## Как разобрать падение

1. Найдите строку с именем провалившегося случая: она укажет сценарий, например B1 или E3.
2. Прочитайте проверку `assert` и значения ниже неё. Если у B1 ожидалось `source_reads == 1`, а получено 2, повторное чтение снова обратилось к источнику.
3. Откройте эту функцию в `tests/`, сопоставьте порядок действий с контрактом задания. Проверьте, какое исходное состояние она создаёт.
4. Исправьте реализацию, сохраните файл и повторите конкретный тест. Затем выполните всю текущую группу и ранее завершённые группы.
5. Запишите итоговый результат в отчёт. Не изменяйте ожидаемое значение, чтобы скрыть дефект.

`passed` — сценарий прошёл; `failed` — условие сценария не выполнено; `deselected` — случай не выбран вашей командой; `error` — выполнение прервалось, например при подготовке окружения. Причину всегда уточняйте по сообщению, а не по одному слову.

Если Redis недоступен, проверьте `docker compose ps` и `docker compose logs redis`. После ручного сценария отказа верните его командой `docker compose start redis`. Если падает сборка или импорт библиотек, сначала устраните ошибку окружения, затем проверяйте поведение сервиса.

## Собственный тест

Для Б+ и выше нужен дополнительный содержательный сценарий. Создайте файл вида `tests/test_my_scenario.py` и функцию `async def test_...`. Можно использовать fixture `factory`, как в открытых примерах. Не меняйте исходные проверки.

Без метки группы ваш тест попадёт в полный запуск, но не в отбор `-m basic`. Поэтому перед сдачей запустите его явно, подставив имя своего файла:

```sh
docker compose run --build --rm tests python -m pytest -q tests/test_my_scenario.py
```

В отчёте поясните, какое поведение проверяется, как тест создаёт нужное состояние и какой дефект он способен обнаружить.
