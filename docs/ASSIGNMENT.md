# Постановка задания

Начните с [README](../README.md): там объяснён контекст, подготовка окружения и действия на каждом этапе. Этот документ уточняет технические требования. Команды тестирования и ожидаемые результаты есть в README и [TESTING.md](TESTING.md).

## Задача

Реализуйте кэш каталога товаров в `app/service.py`. Уменьшите число чтений источника, корректно обработайте обновления и сохраните работоспособность API при сбоях Redis. Поведение должно соответствовать контракту ниже.

Готовые части: HTTP API, модели, источник, Docker Compose и тесты. Можно добавлять вспомогательные модули. Не меняйте HTTP-контракт, конструктор и публичные методы `ProductService`, исходные товары, задержку источника и смысл счётчиков ради прохождения проверок.

## Контракт и границы

| Условие | Требуемое поведение |
|---|---|
| Свежая запись | Вернуть данные из Redis без чтения источника |
| Промах или повреждённая запись | Прочитать источник и сохранить корректную запись с конечным TTL |
| Истёкший TTL в cache-aside | Дождаться нового чтения источника |
| Успешный PATCH | Сначала обновить источник, затем инвалидировать запись именно этого товара |
| GET после завершившегося PATCH | Вернуть обновлённый товар, если между ними не было других обновлений |
| Ошибка Redis GET/SET/DEL | Использовать источник, не превращать работоспособный API в 500 |
| Ошибка самого источника | Не выдавать успех и не подменять результат произвольными данными |
| Redis восстановился после PATCH во время сбоя | Не возвращать сохранённую до изменения цену |
| Несуществующий товар | 404 через уже готовый API; отрицательное кэширование не требуется |

Используйте ключ `{prefix}:product:{id}`. Сериализация JSON и её внутренняя структура выбираются вами. Запись должна содержать сведения о времени истечения, чтобы её можно было проверить через переданную функцию `clock()`. Срок проверяется и в коде, и через Redis TTL. Установите TTL одновременно с записью (`SET ... EX/PX`), чтобы при прерывании не остался бессрочный ключ.

`fresh_ttl` и `stale_ttl` задаются в секундах и могут быть дробными. На границе `now == expires_at` запись уже истекла. В cache-aside полный срок равен `fresh_ttl`. В SWR он равен `fresh_ttl + stale_ttl`.

`clock()` возвращает время в секундах. Тесты могут двигать его без ожидания реального TTL Redis. Не вызывайте напрямую `time.time()` для проверок возраста записи: используйте переданную функцию. Redis TTL нужен для физического удаления, метка времени нужна для логики свежести и детерминированных проверок.

Область гарантий: один процесс API, один event loop, один экземпляр `ProductService`. Запросы с разными ключами независимы. Все изменения каталога в обычном режиме идут через этот сервис. При перезапуске API источник и namespace создаются заново. Ни долговечное хранение заказов, ни многопроцессная согласованность здесь не моделируются.

Сценарий внешнего изменения источника в тестах нужен для демонстрации TTL и SWR. Немедленное обнаружение внешнего изменения не требуется: оно становится видно после обновления кэша.

## Этап 0. Запуск и исходное поведение

План: 30 минут.

Выполните первый запуск по README. API нужен для ручного опыта: сделайте два GET одного товара и сравните `source_reads` до и после. Затем вручную запустите `docker compose run --build --rm tests python -m pytest -q -m smoke` из корня проекта. Ожидаются 2 прошедшие проверки и 20 невыбранных. Тесты используют отдельные объекты и не меняют счётчики демонстрационного API. Прочитайте `app/source.py` и объясните, почему два одинаковых запроса в заготовке дают два чтения источника.

Результат: работающий проект и исходное значение счётчика в `REPORT.md`.

## Этап 1. Cache-aside и TTL

План: 2 часа, включая знакомство с Redis.

Реализуйте чтение Redis, обработку промаха, сериализацию товара и сохранение с TTL. При повторном чтении свежего товара источник не вызывается. После истечения срока первое чтение снова получает товар из источника. Невалидный JSON, `null` и запись неподходящей структуры обрабатываются как промах.

Результат: B1, B2, B6 проходят. Вы можете объяснить, почему бессрочная запись здесь недопустима и почему обычный словарь Python не заменяет Redis в этом задании.

## Этап 2. Изменение товара

План: 1 час.

Реализуйте порядок «изменить источник, затем инвалидировать свой ключ». Успешный PATCH не должен удалять весь кэш или затрагивать второй товар. Проверяйте, что нулевой остаток и нулевая цена остаются корректными значениями.

Результат: B3 проходит. В отчёте есть последовательность GET → PATCH → GET, полученные версии и цена.

На базовом уровне сценарий проверяется последовательно. Координация PATCH с уже выполняющимся фоновым обновлением входит в Э.

## Этап 3. Отказ Redis и восстановление

План: 1,5 часа.

Обработайте ошибки операций Redis. Если кэш недоступен, читайте или обновляйте источник. Не используйте общий `except Exception: return ...`, который скрывает ошибки вашей программы и источника. Таймауты Redis уже настроены в `main.py`.

Отдельно разберите случай: товар закэширован, Redis становится недоступен, PATCH меняет цену, удалить старый ключ не удаётся, Redis восстанавливается. Простого «поймать исключение DEL» недостаточно: старый ключ может ещё существовать.

Допустимые подходы: хранить признак невалидированного ключа и не доверять ему до успешной инвалидации либо временно обходить кэш до истечения максимального срока его прежних записей. Выберите подход, реализуйте его и объясните. Он должен работать в пределах одного процесса и конечного TTL. При восстановлении старую цену возвращать нельзя.

Результат: B4, B5, B7 проходят. Вы воспроизводите остановку Redis командами из README и описываете политику восстановления.

## Этап 4. Эксперимент и базовый отчёт

План: 1 час.

Сравните число чтений источника для серии одинаковых запросов с исходной заготовкой и вашим решением. Зафиксируйте исходное состояние, число запросов, выбранный TTL и разницу `source_reads`. Например, при 20 последовательных GET одного товара в пределах TTL ожидаются 20 чтений без кэша и 1 с кэшем. Это ожидаемый результат, собственные измерения внесите в отчёт отдельно.

Объясните один компромисс: длинный TTL снижает нагрузку, но увеличивает период незаметных внешних изменений. Длительность запросов можно измерить дополнительно; абсолютные миллисекунды не определяют оценку.

Результат: вся группа `basic` проходит, заполнены базовые разделы отчёта.

## Этап 5*. Защита от cache stampede, уровень П

План: 1,5 часа.

При 20 одновременных запросах одного отсутствующего в кэше товара и доступном Redis выполните одно чтение источника. Остальные запросы должны получить этот результат. Решение действует на один ключ и один процесс.

Используйте блокировку на ключ или разделяемую задачу загрузки. При использовании блокировки повторно проверяйте кэш после входа в неё. Запрос товара 2 не должен ждать медленную загрузку товара 1. Отмена запроса не должна оставлять вечную блокировку.

Результат: P1–P3 проходят, в отчёте есть конкурентный эксперимент. Объясните, почему локальная `asyncio.Lock` сама по себе не защищает от stampede при двух независимых процессах API.

Защищать источник от общей перегрузки во время отказа Redis в этом этапе не требуется. Это другая задача, например ограничение конкурентности или admission control.

## Этап 6*. Stale-while-revalidate, уровень Э

План: 2 часа.

Добавьте режим `swr`, сохранив работу `cache_aside`. Возраст записи определяет поведение:

| Возраст | Действие |
|---|---|
| Меньше `fresh_ttl` | Вернуть свежий кэш |
| От `fresh_ttl` до `fresh_ttl + stale_ttl` | Сразу вернуть допустимо устаревший кэш и запустить одно обновление в фоне |
| Не меньше `fresh_ttl + stale_ttl` | Дождаться источника, устаревшее значение не возвращать |

Пока фоновый запрос ожидает источник, следующие читатели всё ещё получают допустимо устаревший результат. Они не должны ждать блокировку фонового обновления. Одновременные запросы запускают не более одного обновления на ключ.

Согласуйте PATCH и обновление кэша. Старый результат ранее начавшегося refresh не должен перезаписать более новое значение после завершения PATCH. Допустимо сериализовать refresh и PATCH на ключ либо использовать проверку версии. Немедленный ответ PATCH во время refresh не требуется.

Сохраните ссылки на фоновые задачи, регистрируйте ошибки в логах. `wait_idle()` ожидает уже запущенные обновления. `aclose()` завершает или отменяет фоновые задачи без зависания на заблокированном источнике; Redis-клиент закрывает вызывающая сторона. Ошибка refresh не продлевает максимальный срок старой записи.

Результат: E1–E5 проходят. В отчёте объяснено, где устаревшие данные допустимы. SWR пригоден, например, для описания товара; финальную цену и доступность при оформлении заказа надо перепроверять в основном источнике.

План: 1 час.

Запустите соответствующие вашему уровню проверки, заполните отчёт, запишите видео до четырёх минут и создайте Pull Request по [инструкции сдачи](SUBMISSION.md) в `rbeketov/redis-cache-lab:main`. Укажите выполненные и невыполненные этапы без умолчаний.

## Критерии готовности

- Проект запускается по README без ручного редактирования контейнеров.
- Smoke и все тесты заявленного уровня проходят.
- Реализация действительно читает и пишет Redis, сохраняет TTL и не меняет проверки ради результата.
- Отчёт содержит наблюдения, политику восстановления и границы гарантий.
- Видео показывает код, работу приложения и проверку результата.
- Pull Request содержит ссылку на видео, краткое описание и команды быстрой проверки.
