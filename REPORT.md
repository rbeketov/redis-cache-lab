## Измерения

Значения `source_reads` снимались через `/debug/stats` до и после серии. Перед исходным опытом и перед опытом готового cache-aside API был пересоздан; внутри каждой серии перезапуска не было. SWR проверялся в отдельном новом процессе API.

| Сценарий | Число GET | Состояние / TTL | Чтений источника | Вывод |
|---|---:|---|---:|---|
| Исходная заготовка | 20 | Новый процесс, товар 1 | 20 (0 → 20) | Каждый запрос читает источник |

Порядок cache-aside опытов: последовательные → истечение → PATCH → конкурентные → сбой → восстановление. PATCH изменил цену с 49900 до 55000 и остаток с 20 до 0; следующий GET подтвердил оба поля и revision=2. Во время сбоя PATCH установил цену 61000 и revision=3.

При остановке Redis его данные теряются по настройкам Compose. Сохранение старого ключа при сетевом сбое отдельно проверено B5 и собственными сценариями с реальным Redis под обёрткой, которая вызывает ошибки команд.

В HTTP-опыте SWR источник не изменялся, поэтому версия товара осталась 1; счётчик подтвердил одно обновление. Возврат старой версии с последующим переходом к новой проверен E1: источник изменён напрямую, чтение остановлено событием, stale-запросы не ждут его завершения.

Для повторения последовательной серии после пересоздания API можно выполнить в Python внутри контейнера:

```python
import json
from urllib.request import urlopen

def get(path):
    with urlopen("http://127.0.0.1:8000" + path) as response:
        return json.load(response)

before = get("/debug/stats")["source_reads"]
for _ in range(20):
    get("/products/1")
print(get("/debug/stats")["source_reads"] - before)
```

## Решения и гарантии

1. **Формат и TTL.** Ключ `{prefix}:product:{id}` содержит JSON с `product`, `fresh_until` и `expires_at`. Pydantic проверяет структуру, поля товара и конечность временных меток; также проверяются id и порядок сроков. Повреждённая запись считается промахом. При записи используется один `SET ... PX`, миллисекунды округляются вверх; логическое истечение проверяется строго по `clock()`, включая равенство границе. В cache-aside полный срок равен fresh TTL, в SWR — сумме fresh и stale TTL. Длинный TTL уменьшает нагрузку, но дольше скрывает внешние изменения. Учебный TTL 5 с позволяет быстро наблюдать этот компромисс. Redis общий для клиентов и удаляет записи по TTL; словарь Python не подтверждает работу с Redis и не заменяет его в задании.

2. **PATCH.** Изменение источника и последующее удаление своего ключа выполняются под блокировкой товара. Другие ключи не удаляются. Перед первым ожиданием устанавливается локальная метка недоверия: даже отмена во время записи или DEL не позволит следующему GET использовать прежний кэш. Фактический DEL выполняется после успешного обновления источника.

3. **Сбои.** Перехватываются только `RedisError` от операций Redis, с записью в лог. При ошибке GET читается источник, при ошибке SET возвращается уже полученный товар, при ошибке DEL сохраняется метка недоверия. Пока DEL не успешен, GET повторяет инвалидацию и читает источник без записи кэша. Ошибки источника передаются вызывающему коду; неизвестный товар получает 404 через готовый API. Общего подавления исключений нет.

4. **Восстановление.** Ключ с меткой недоверия никогда не используется. При первом успешном DEL старая запись удаляется, затем источник читается заново. Если SET после DEL не удался, следующий GET также получит промах. Другие товары сохраняют свой кэш. Цена этой политики — дополнительные чтения источника и попытки DEL до восстановления; это сознательный выбор доступности и корректности вместо использования сомнительной копии. Локальная метка живёт в процессе; после перезапуска создаётся новый namespace.

5. **Согласованность.** GET, начавшийся после завершившегося PATCH, получает обновлённую версию при отсутствии последующих записей. Уже выполнявшийся GET может вернуть прежнюю версию. Внешние изменения видны после TTL/refresh; немедленного обнаружения нет. В SWR старые данные допустимы только до жёсткого срока. Для оформления заказа цену и доступность нужно проверять у источника. Гарантия ограничена одним экземпляром сервиса, процессом и event loop.

6. **Конкурентность.** `asyncio.Lock` создаётся на товар; после входа кэш проверяется повторно. 20 промахов одного ключа при работающем Redis дают одно чтение. Разные товары не ждут друг друга. Контекст блокировки освобождает её при отмене; слабые ссылки удаляют неиспользуемые блокировки. В двух процессах локальные блокировки независимы, поэтому для общей координации понадобился бы отдельный распределённый механизм. При недоступном Redis объединение всех промахов в одну загрузку не гарантируется, как допускает условие.

7. **SWR и завершение.** При `now < fresh_until` возвращается свежая запись. При `fresh_until <= now < expires_at` сразу возвращается stale-значение и планируется одна задача на ключ. При `now >= expires_at` запрос ждёт источник. Stale-читатели обходят блокировку refresh. Загрузка, публикация и PATCH используют одну блокировку: старый refresh заканчивается до PATCH, а PATCH удаляет его результат; refresh, начавшийся после PATCH, читает актуальный источник. Ошибки фоновых задач извлекаются и логируются, не продлевая срок старой записи. `wait_idle()` ждёт снимок уже запланированных задач; `aclose()` запрещает новые refresh, отменяет существующие и дожидается их, в том числе при заблокированном источнике. Redis-клиент закрывает вызывающая сторона.

## Собственный тест для Б+ и выше

В `tests/test_resilience.py` добавлены 9 случаев:

- `test_cancelled_invalidation_keeps_old_entry_untrusted`: PATCH уже изменил источник, DEL блокируется и запрос отменяется. Старая запись физически остаётся в Redis; следующий GET обязан вернуть новую нулевую цену. Выявляет потерю защиты при отмене между записью и инвалидацией.
- `test_failed_delete_preserves_other_key_and_recovers_after_failed_set`: DEL одного товара не работает, затем DEL восстанавливается раньше SET. Проверяет новую версию на всех стадиях и сохранность кэша второго товара.
- `test_foreground_fill_cannot_overwrite_a_completed_patch`: обычная холодная загрузка захватила старую версию, а PATCH начался до её завершения. После PATCH кэш не должен содержать старый снимок.
- `test_fractional_ttl_and_exact_expiry_boundary` (2 случая): TTL 0.25 с, stale-окно 0 или 0.5 с; проверяет физический TTL, точную границу свежести и окончательного истечения.
- `test_fresh_swr_reads_do_not_schedule_background_work`: после прогрева источник намеренно ломается; свежие конкурентные GET не должны запускать лишний refresh.
- `test_structurally_valid_but_unusable_entry_is_replaced` (3 случая): чужой id, NaN во времени истечения и обратный порядок сроков должны привести к загрузке и исправлению записи.
