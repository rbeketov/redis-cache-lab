## Решения и гарантии

### Формат и срок хранения

Ключ имеет вид `{prefix}:product:{id}`. JSON содержит `product`, `fresh_until` и `expires_at`. Проверяются модель товара, конечные временные метки, совпадение ID и порядок границ. Невалидная запись считается промахом.

Возраст проверяется через переданный `clock()`. При равенстве текущего времени границе соответствующий срок уже истёк. Redis получает TTL атомарно с `SET ... PX`; дробные секунды округляются вверх до миллисекунд. Логическая проверка времени сохраняет точную границу независимо от этого округления.

В cache-aside полный срок равен `fresh_ttl`, в SWR — `fresh_ttl + stale_ttl`. Более длинный TTL уменьшает число чтений, но увеличивает период, в котором внешнее изменение источника может оставаться незаметным. Бессрочный кэш этого ограничения не даёт.

### Изменение и восстановление

PATCH под блокировкой товара сначала изменяет источник, затем отмечает ключ как недостоверный и вызывает DEL. Успешный DEL снимает отметку. При ошибке отметка остаётся: такой ключ не читается, перед следующей загрузкой сервис повторяет инвалидацию. Пока DEL не сработал, товар берётся из источника и старая запись не используется.

При ошибке GET выполняется чтение источника. Ошибка SET не отменяет полученный из источника ответ. Ошибка DEL не отменяет уже выполненный PATCH. Ошибки Redis логируются. Ошибки самого источника в обычном GET/PATCH распространяются вызывающему коду; неизвестный товар обрабатывается готовым API как 404.

Цена этой политики — дополнительные обращения к источнику для недостоверного ключа при длительном сбое DEL. Другие ключи остаются доступны через кэш. Защита опирается на локальную отметку и область одного процесса; перезапуск создаёт новый источник и namespace.

### Конкурентность и SWR

Для каждого товара используется отдельная `asyncio.Lock`. После её получения кэш проверяется повторно. Поэтому при доступном Redis конкурентные промахи одного ключа используют одну загрузку. Разные товары не разделяют блокировку. При отказе Redis ограничение общей нагрузки на источник не реализовано и заданием не требуется. Независимые процессы имеют разные блокировки: многопроцессная защита от stampede не гарантируется.

SWR отдаёт свежую запись без обновления. В stale-окне GET сразу возвращает старый товар и запускает не более одного refresh на ключ. Последующие stale-читатели не ждут блокировку фоновой загрузки. После `expires_at` старое значение не возвращается: GET ждёт источник.

Refresh и PATCH используют одну блокировку товара. Если refresh начался первым, PATCH ждёт его, затем меняет источник и удаляет старый кэш. Если PATCH прошёл первым, refresh читает состояние после него. Старый результат refresh поэтому не может записаться после завершившегося PATCH. Немедленное завершение PATCH во время refresh не обещается.

Ошибка фонового обновления логируется и не продлевает исходный stale-срок. После окончательного истечения ошибка источника становится ошибкой GET. `wait_idle()` ждёт уже запланированные задачи; отмена ожидания не отменяет refresh. `aclose()` запрещает новые фоновые обновления, отменяет и дожидается существующих задач, включая заблокированные в источнике. Redis-клиент закрывается вызывающей стороной.

Гарантии действуют для одного экземпляра сервиса в одном процессе/event loop, когда изменения проходят через сервис. Внешние изменения обнаруживаются при следующей загрузке. SWR подходит для допускающих временное устаревание данных; финальную цену и наличие при оформлении заказа следует перепроверять в основном источнике.
