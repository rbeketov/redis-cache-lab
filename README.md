# Кэширование каталога товаров с Redis

В этой работе вы доработаете готовое приложение: оно научится повторно использовать недавно полученные данные о товарах, сохраняя возможность изменять их и работать при сбоях. Ниже описан весь путь от первого запуска до сдачи решения.

**Трудоёмкость:** около 7 часов на обязательную часть со сдачей, 10–12 часов с дополнительными этапами.

## Контекст и результат

Представьте интернет-магазин. Чтобы показать карточку товара, приложение узнаёт его название, цену и количество на складе у основного источника данных. Таким источником может быть база магазина или другой сервис. Каждое обращение занимает время и создаёт нагрузку. Если много людей смотрят один товар, приложение многократно запрашивает одинаковые сведения.

Можно некоторое время хранить уже полученную копию рядом с приложением и отвечать на повторные запросы с её помощью. Такое временное хранилище называется **кэшем**. В нашей работе его роль выполняет **Redis** — отдельная программа, которая позволяет быстро сохранять и получать данные по имени записи.

Но копия может устареть: например, магазин изменил цену. Временное хранилище также может перестать отвечать, а несколько покупателей могут запросить один товар одновременно. Поэтому недостаточно просто сохранить ответ. Нужно определить, как долго ему доверять, когда получать данные заново и что делать при сбое.

Вы будете решать эти задачи на небольшом каталоге. На выходе ожидается приложение, которое реже обращается к основному источнику, показывает новую цену после её изменения и продолжает обслуживать запросы при недоступности Redis. В дополнительных этапах вы уменьшите число повторных загрузок при одновременных запросах и добавите обновление копии в фоне.

Результат подтверждается работающим кодом, проверками и вашим сравнением числа обращений к источнику до и после доработки. В отчёте вы объясните, какие гарантии даёт решение и в каких случаях сведения могут временно устаревать.

## Что понадобится и как это используется

Предполагается, что вы умеете читать простую программу на Python: функции, классы и обработку исключений. Желательно знать `async`/`await`: в задании программа ожидает ответы других компонентов, а в дополнительных этапах выполняет несколько операций одновременно. Опыт Redis не требуется; термины вводятся по ходу работы.

Данные между компонентами передаются в JSON — текстовой записи полей и значений. В HTTP-интерфейсе приложения запрос `GET` читает товар, а `PATCH` изменяет часть его полей. Вам уже даны готовые обработчики этих запросов, поэтому писать веб-приложение с нуля не нужно.

| Инструмент | Для чего нужен здесь | Что сделать до начала |
|---|---|---|
| Git 2.23+ и аккаунт GitHub | Получить задание, сохранить изменения, отправить код на проверку | Установить [Git](https://git-scm.com/downloads) и войти в GitHub |
| Docker Engine 24+ или Docker Desktop | Запустить изолированное окружение с нужными версиями программ | Установить [Docker](https://docs.docker.com/get-started/get-docker/) и запустить его |
| Docker Compose 2.20+ | Одной командой запускать связанные компоненты проекта | Проверить `docker compose version`; в Docker Desktop Compose уже включён |
| Редактор, например VS Code | Изменять Python-файлы и заполнять отчёт | Открыть в редакторе папку своей копии проекта |
| Терминал bash/zsh | Выполнять приведённые команды | На Windows использовать WSL2 с интеграцией Docker Desktop |
| `curl` или браузер | Отправлять запросы приложению и смотреть ответы | Проверить `curl --version`; для запросов также доступна страница `/docs` |

Все команды ниже выполняются **в терминале вашего компьютера**, а не внутри интерактивной сессии контейнера и не в консоли Python. После клонирования выполняйте их из папки `redis-cache-lab`, где лежит `compose.yaml`. Сам Python, Redis и тестовая программа будут работать в контейнерах; устанавливать их отдельно на компьютер не требуется.

Ориентиры для компьютера: 2 ядра, 4 ГБ доступной памяти, 3 ГБ свободного места. Первый запуск требует доступа к Docker Hub и PyPI для загрузки образов и библиотек.

## Получение своей копии

**Fork** — ваша копия репозитория на GitHub. **Клонирование** переносит её на компьютер. **Ветка** позволяет сохранить своё решение отдельно от исходной заготовки.

1. [Создайте fork](https://github.com/rbeketov/redis-cache-lab/fork) в своём аккаунте, оставив имя `redis-cache-lab`.
2. Откройте терминал в папке, куда хотите сохранить проект.
3. Замените `your-github-login` своим логином и выполните:

```sh
GITHUB_USER=your-github-login
git clone "https://github.com/$GITHUB_USER/redis-cache-lab.git"
cd redis-cache-lab
git remote add upstream https://github.com/rbeketov/redis-cache-lab.git
git switch -c solution/redis-cache
git remote -v
```

В выводе `origin` должен указывать на ваш аккаунт, `upstream` — на `rbeketov`. Если fork назван иначе, возьмите его адрес через кнопку **Code** на GitHub. Все следующие действия выполняйте в созданной папке и ветке `solution/redis-cache`.

## Устройство учебного проекта

Здесь начинаются детали реализации. Приложение предоставляет **API** — набор HTTP-адресов для чтения и изменения товаров. Docker запускает программу в **контейнере**, то есть в окружении с собственными библиотеками. **Образ** — подготовленная основа, из которой создаётся контейнер.

В `compose.yaml` описаны три компонента:

| Имя | Что выполняет | Как запускается |
|---|---|---|
| `api` | Готовое приложение на FastAPI и основной источник товаров | `docker compose up --build -d api` |
| `redis` | Временное хранилище | Compose запускает его как зависимость `api` или `tests` |
| `tests` | Программа pytest, проверяющая ваше решение | Отдельной ручной командой `docker compose run --build --rm tests ...` |

Основной источник — готовый Python-объект из `app/source.py` с двумя товарами. Он намеренно задерживает чтение на 100 мс и считает обращения. Это позволяет увидеть пользу кэширования, не настраивая дополнительную базу данных. Кэш предстоит реализовать в `app/service.py`.

| Файл | Ваша работа с ним |
|---|---|
| `app/service.py` | Изменять методы `ProductService`, здесь находятся подсказки TODO |
| `app/source.py` | Прочитать устройство источника и счётчиков; не менять их ради тестов |
| `app/main.py` | Посмотреть готовые HTTP-адреса, создание Redis-клиента и таймауты |
| `app/models.py` | Посмотреть поля товара и допустимые изменения |
| `app/settings.py` | Посмотреть настройки; обычно менять файл не требуется |
| `tests/` | Читать сценарии и выполнять проверки; собственные тесты добавлять отдельными файлами |
| `requirements.lock`, `Dockerfile` | Фиксируют Python-зависимости и сборку окружения |

**Ограничения модели.** API работает в одном процессе с одним циклом выполнения асинхронных задач. Товары хранятся в памяти, поэтому перезапуск API возвращает исходные цены, остатки и счётчики. После каждого запуска создаётся новый префикс имён записей Redis — отдельное пространство ключей, чтобы не использовать копии от прежнего запуска. Координация нескольких серверов и долговременное хранение товаров в задание не входят.

## Сборка и первый запуск

Сначала убедитесь, что инструменты доступны:

```sh
git --version
docker version
docker compose version
curl --version
```

`docker version` должен показывать сведения и о клиенте, и о сервере Docker. Если сервер недоступен, запустите Docker Desktop или Docker Engine и повторите проверку.

Теперь соберите и запустите приложение:

```sh
docker compose up --build -d api
docker compose ps
curl --fail --retry 10 --retry-connrefused --retry-delay 1 http://localhost:8000/health
```

`--build` собирает образ из текущих файлов проекта; `-d` оставляет приложение работать в фоне. Compose сначала ждёт готовности Redis. В `ps` у `api` должен быть статус `Up`, у Redis — `healthy`. Команда `curl` допускает короткое ожидание старта API. Ожидаемый ответ:

```json
{"status":"ok","mode":"cache_aside"}
```

`cache_aside` — название основного режима задания; его алгоритм объясняется в этапе 1. Сам ответ `/health` подтверждает доступность приложения, но ещё не доказывает, что кэширование реализовано.

Откройте [http://localhost:8000/docs](http://localhost:8000/docs). Здесь можно выбрать запрос, нажать **Try it out**, ввести параметры и нажать **Execute**. Это альтернатива `curl` для ручных проверок.

В контейнерах используются Python 3.12.10, Redis 7.4.2, FastAPI 0.115.12, redis-py 5.2.1 и pytest 8.3.5. Все Python-зависимости зафиксированы в `requirements.lock`. Redis доступен только внутри сети Compose, API — на `127.0.0.1:8000` вашего компьютера.

## Как запускаются проверки

**Вы запускаете тесты вручную, а проверку ожидаемого результата выполняет pytest автоматически.** Запуск API, сохранение файла, commit или отправка кода в GitHub сами по себе тесты не запускают. Автоматического процесса проверки на GitHub в этом репозитории пока нет.

Первая проверка:

```sh
docker compose run --build --rm tests python -m pytest -q -m smoke
```

`run` создаёт отдельный тестовый контейнер, `--build` подготавливает его образ, `--rm` удаляет контейнер после завершения. `python -m pytest` запускает проверяющую программу, `-q` сокращает вывод, `-m smoke` выбирает группу первичных проверок. Уже запущенное API на порту 8000 для этой команды не требуется.

Тестовый контейнер использует **сохранённые файлы вашей текущей рабочей папки**, подключённой в `/workspace`, в том числе изменения, ещё не попавшие в commit. GitHub-код не скачивается при каждом запуске тестов. Перед командой сохраните изменения в редакторе.

Тесты подключаются к настоящему Redis из Compose. Они создают собственные экземпляры источника и сервиса с уникальными ключами. HTTP-проверка обращается к приложению внутри тестового процесса, не к вашему открытому порту 8000. Поэтому тесты не меняют товары и счётчики демонстрационного API. Для ошибок соединения и порядка одновременных действий предусмотрены управляемые условия, описанные в [TESTING.md](docs/TESTING.md).

| Группа | Файл | Что проверяет | Число случаев |
|---|---|---|---:|
| `smoke` | `test_smoke.py` | Готовый источник, чтение/изменение товара через API, ответы на неверные запросы | 2 |
| `basic` | `test_basic.py` | Повторное чтение, срок хранения, изменение товара, ошибки Redis и повреждённые записи | 12 |
| `advanced` | `test_advanced.py` | Одновременные запросы одного товара, независимость товаров и отмена запроса | 3 |
| `expert` | `test_expert.py` | Фоновое обновление, предел устаревания, совместная работа обновлений и остановка задач | 5 |

В исходном наборе 22 случая: некоторые тестовые функции запускаются с несколькими входными значениями. На неизменённой заготовке команда `-m smoke` должна закончиться строкой `2 passed, 20 deselected` и временем выполнения. `passed` означает успешную проверку, `deselected` — проверки других групп, которые эта команда не выбирала.

Остальные группы могут падать до выполнения соответствующих этапов — так тесты показывают отсутствующую функциональность. Ошибка `FAILED` после сравнения ожидаемого и фактического результата обычно относится к решению; `ERROR` при подготовке окружения требует сначала разобраться с запуском. Отключение проверки не считается исправлением. Порядок чтения вывода и запуск отдельного случая есть в [TESTING.md](docs/TESTING.md).

## Порядок выполнения

На каждом этапе есть действие, команда проверки и критерий завершения. Выполняйте команды из корня своей копии проекта. Точный контракт методов и границы поведения уточняются в [ASSIGNMENT.md](docs/ASSIGNMENT.md).

### Этап 0. Зафиксировать исходное поведение — 30 минут

1. Выполните разделы получения копии, сборки и первичной проверки выше.
2. Откройте `app/service.py`: методы `get` и `update` пока обращаются напрямую к источнику. Сопоставьте их с `get` и `update` в `app/source.py`.
3. После свежего запуска API выполните весь блок:

```sh
curl --fail http://localhost:8000/debug/stats
curl --fail http://localhost:8000/products/1
curl --fail http://localhost:8000/products/1
curl --fail http://localhost:8000/debug/stats
```

Адрес `/debug/stats` возвращает счётчики: `source_reads` — число чтений источника, `source_writes` — число изменений. Сам запрос статистики их не увеличивает. В заготовке два чтения товара увеличивают `source_reads` на 2. Если до этого вы уже проверяли API, сравнивайте разницу, а не абсолютное значение.

**Готово, когда:** smoke проходит, вы видите товар 1 с ценой `49900` копеек и можете объяснить два обращения к источнику. Запишите команду и исходные измерения в `REPORT.md`, чтобы затем сравнить их с решением.

### Этап 1. Повторное использование данных и срок хранения — 2 часа

Теперь введём названия механизмов. **Cache-aside** — порядок «сначала искать копию в Redis, а при её отсутствии читать источник и сохранять копию». Найденную пригодную запись называют **cache hit**, отсутствие пригодной записи — **cache miss**. **TTL** — время жизни записи, после которого ей больше нельзя доверять.

1. В `ProductService.get` реализуйте этот порядок. Для сохранения товара используйте JSON; имя ключа и обязательные параметры заданы в контракте.
2. Ограничьте срок записи и в Redis, и при чтении её метки времени. Пользуйтесь переданной функцией `clock()`, чтобы тесты могли проверять истечение срока без долгого ожидания.
3. Если запись испорчена или имеет неверную структуру, получите товар заново. Не меняйте готовый источник для получения нужного счётчика.
4. Сохраните файл и запустите:

```sh
docker compose run --build --rm tests python -m pytest -q tests/test_basic.py -k 'b1_ or b2_ or b6_'
```

Здесь `-k` выбирает проверки по фрагментам имени. **Готово, когда:** 6 выбранных случаев проходят; два последовательных чтения внутри срока жизни дают одно чтение источника, после истечения срока выполняется новое чтение. Запишите формат вашей записи и выбранный срок в отчёт.

### Этап 2. Изменение цены и удаление старой копии — 1 час

Удаление копии, которой больше нельзя доверять, называется **инвалидацией**. В методе `ProductService.update` сначала измените источник и затем удалите запись именно этого товара. Остальные товары должны оставаться в кэше.

После сохранения кода перезапустите API по инструкции ниже, дождитесь ответа `/health` и выполните:

```sh
curl --fail http://localhost:8000/products/1
curl --fail -X PATCH http://localhost:8000/products/1 \
  -H 'Content-Type: application/json' -d '{"price_kopecks":55000,"stock":7}'
curl --fail http://localhost:8000/products/1
docker compose run --build --rm tests python -m pytest -q tests/test_basic.py -k b3_
```

`price_kopecks` — цена в копейках, `stock` — остаток, `revision` — версия товара. После свежего запуска первый PATCH даёт версию 2. **Готово, когда:** следующий GET возвращает цену 55000 и остаток 7, а выбранный тест проходит. Нулевой остаток и нулевая цена также допустимы.

### Этап 3. Работа при отказе Redis — 1,5 часа

В `get` и `update` обработайте ошибки операций с Redis. Приложение должно использовать основной источник. Отдельно продумайте ситуацию: источник уже изменён, удалить старую копию не удалось, затем Redis снова стал доступен. Следующий GET не должен вернуть старую цену. Возможные политики восстановления описаны в постановке.

```sh
docker compose run --build --rm tests python -m pytest -q tests/test_basic.py -k 'b4_ or b5_ or b7_'
```

**Готово, когда:** все 5 выбранных случаев проходят, ошибки источника не маскируются успешным ответом. В отчёте объясните, что происходит при ошибке чтения, записи и удаления в Redis. После этого выполните ручной сценарий из раздела «Проверка отказа Redis» ниже.

### Этап 4. Сравнение с исходным поведением — 1 час

Нужно показать уменьшение числа чтений источника. Не сравнивайте случайно разные начальные состояния. Для повторяемого опыта начните со свежего процесса и задайте срок хранения 60 секунд, чтобы серия запросов успела закончиться до его истечения:

```sh
CACHE_MODE=cache_aside FRESH_TTL=60 docker compose up --build -d --force-recreate api
curl --fail --retry 10 --retry-connrefused --retry-delay 1 http://localhost:8000/health
curl --fail http://localhost:8000/debug/stats
for ((i=0; i<20; i++)); do
  curl --fail --silent --show-error http://localhost:8000/products/1 > /dev/null || break
done
curl --fail http://localhost:8000/debug/stats
```

Цикл отправляет 20 запросов по очереди. Если команда вывела ошибку, исправьте её и повторите опыт с начала. Ожидается прирост `source_reads` на 20 у исходной заготовки и на 1 у реализованного кэша, если вся серия уложилась в 60 секунд. Для исходного измерения этот же блок можно выполнить на этапе 0 до редактирования кода; не заменяйте собственное измерение ожидаемым числом. Если исходный опыт не записан, укажите это в отчёте.

Запишите число запросов, срок хранения, счётчики до/после и вывод. Поясните, чем приходится платить за более долгий срок хранения копии. Восстановите настройки по умолчанию командой `docker compose up -d --force-recreate api` и выполните:

```sh
docker compose run --build --rm tests python -m pytest -q -m 'smoke or basic'
```

**Готово, когда:** 14 проверок проходят и заполнены базовые разделы отчёта. Для уровня Б+ дополнительно нужен собственный содержательный тест нового сценария и объяснение компромисса выбранного решения; условия приведены в критериях оценки.

### Этап 5*. Одновременные запросы одного товара — 1,5 часа

Если много запросов одновременно не находят копию, каждый может начать чтение источника. Это называют **cache stampede**. В рамках одного процесса объедините такие обращения, чтобы при доступном Redis 20 запросов одного товара вызвали одну загрузку.

Доработайте `get`, используя блокировку на товар или общую задачу загрузки. Для блокировки понадобится `asyncio.Lock`; после её получения ещё раз проверьте кэш. Другой товар не должен ждать эту загрузку, а отмена запроса не должна оставлять блокировку навсегда.

```sh
docker compose run --build --rm tests python -m pytest -q -m advanced
```

**Готово, когда:** все 3 проверки проходят, обязательная часть по-прежнему работает. В отчёте объясните результат конкурентного опыта и почему локальная блокировка не координирует два разных процесса. Это дополнительный этап для уровня П.

### Этап 6*. Обновление в фоне — 2 часа

**Stale-while-revalidate (SWR)** — режим, в котором некоторое время разрешено отдать старую копию, одновременно запустив её обновление. После окончательного срока старую копию возвращать нельзя, нужно дождаться источника.

В режиме `swr` разделите возраст записи на свежий, допустимо устаревший и окончательно истёкший. Доработайте `get`, координацию с `update`, ожидание фоновых задач в `wait_idle` и их остановку в `aclose`. Точные границы и сценарий конфликта с изменением товара даны в постановке.

```sh
docker compose run --build --rm tests python -m pytest -q -m expert
```

Тесты сами включают `swr` для своих экземпляров сервиса. Для ручной демонстрации включите его отдельно:

```sh
CACHE_MODE=swr docker compose up --build -d --force-recreate api
curl --fail --retry 10 --retry-connrefused --retry-delay 1 http://localhost:8000/health
```

Ожидается `"mode":"swr"`. **Готово, когда:** 5 экспертных проверок и предыдущие уровни проходят. В отчёте объясните допустимый период устаревания, ошибку фонового обновления и согласование с изменением цены. Это этап для Э.

### Этап 7. Итоговая проверка и сдача — 1 час

Запустите набор своего уровня: для Б/Б+ — `smoke or basic`, для П — `smoke or basic or advanced`, для Э — все тесты. Команды приведены в [инструкции сдачи](docs/SUBMISSION.md). Собственный тест запустите отдельно по имени файла, если он не отмечен одной из этих групп.

Заполните отчёт реальными результатами, запишите ролик до четырёх минут, загрузите код в свой fork и откройте **Pull Request** — запрос на проверку ваших изменений — в `rbeketov/redis-cache-lab:main`. Ссылка на ролик входит в описание PR. **Готово, когда:** эксперт может получить именно показанный код, повторить ваши команды и открыть видео без запроса доступа.

## Что делать после изменения файлов

| Что изменили | Как проверить актуальную версию |
|---|---|
| Python-код | Сохранить файлы и запустить нужную команду `tests`: она читает текущую папку |
| Python-код для ручной демонстрации | `docker compose restart api`, затем дождаться `/health`; автоматической перезагрузки кода нет |
| `Dockerfile` или зависимости | Пересобрать: `docker compose build api tests`, затем `docker compose up -d api` |
| Настройки окружения | Выполнить `up -d --force-recreate api` с нужными переменными; простой `restart` их не обновит |

После перезапуска API используйте команду ожидания `/health` из первого запуска. Учтите, что это сбрасывает демонстрационные товары и счётчики. Не делайте перезапуск между двумя частями одного измерения.

Проверяемая версия определяется текущими файлами на диске, а воспроизводимая версия для сдачи — вашим commit. Посмотреть его и отличия:

```sh
git rev-parse HEAD
git status --short
```

Если `status` не пуст, укажите, что проверки выполнялись с локальными изменениями; перед сдачей сохраните код в commit. Версии внутри контейнера можно проверить командой `docker compose run --rm tests python -m pip freeze`. Обычно менять зависимости в этом задании не требуется; их точный список хранится в `requirements.lock`.

## Проверка отказа Redis вручную

Сначала запустите API и выполните GET товара. Затем, сохраняя тот же процесс API:

```sh
docker compose stop redis
curl --fail http://localhost:8000/products/1
curl --fail -X PATCH http://localhost:8000/products/1 \
  -H 'Content-Type: application/json' -d '{"price_kopecks":61000}'
docker compose start redis
docker compose exec redis redis-cli ping
curl --fail http://localhost:8000/products/1
```

После старта Redis дождитесь ответа `PONG` на команду `ping`; если он ещё не готов, повторите её. Приложение должно отвечать при остановленном Redis, а последний GET — показывать цену 61000. Таймауты клиента Redis уже ограничены 0,2 секунды, автоматические повторы отключены. При отказе хранилища число чтений источника может возрасти.

В этой конфигурации Redis после остановки теряет записи. Поэтому ручной опыт проверяет доступность API, но сам по себе не доказывает защиту от возврата сохранившейся старой цены. Тест B5 отдельно моделирует недоступность соединения с сохранением прежнего ключа.

## Настройки

Переменные перед командой запуска переопределяют значения из Compose. Например, `FRESH_TTL=60` используется для опыта выше. Эти переменные настраивают демонстрационный API; тесты задают собственные параметры непосредственно при создании сервиса.

| Переменная | По умолчанию | Назначение |
|---|---:|---|
| `CACHE_MODE` | `cache_aside` | Основной режим или `swr` для дополнительного этапа |
| `FRESH_TTL` | 5 | Сколько секунд копия считается свежей |
| `STALE_TTL` | 10 | Дополнительный период допустимого устаревания, только SWR |
| `SOURCE_DELAY` | 0.1 | Задержка чтения источника в секундах |
| `API_PORT` | 8000 | Порт для доступа к API с компьютера |

При свободном порте 8010 вместо занятого 8000: `API_PORT=8010 docker compose up -d --force-recreate api`. Далее замените порт на 8010 в браузере и командах `curl`. Не меняйте задержку источника ради достижения нужного результата тестов.

## Если что-то не получается

| Наблюдение | Что проверить и сделать |
|---|---|
| `Cannot connect to the Docker daemon` | Запустить Docker Desktop/Engine, дождаться готовности, повторить `docker version` |
| `no configuration file provided` | Перейти в папку проекта с `compose.yaml` |
| Не загружается образ или пакет | Проверить доступ к Docker Hub/PyPI и настройки сети Docker; это этап сборки, код задания ещё не выполняется |
| `port is already allocated` | Выбрать другой `API_PORT` по инструкции выше |
| `curl` не соединяется с API | Проверить `docker compose ps`, дождаться старта, посмотреть `docker compose logs api` |
| `ERROR` подключения к Redis в тестах | После ручного сбоя вернуть Redis: `docker compose start redis`; проверить `docker compose ps` и повторить тест |
| `FAILED` в выбранной проверке | Прочитать имя случая, ожидаемое/фактическое значение и сценарий; инструкция есть в TESTING.md |
| После правки вручную видно старое поведение | Сохранить файл, перезапустить API и дождаться `/health` |
| После перезапуска исчезли изменения цены | Это ожидаемо: учебный источник находится в памяти; повторить демонстрацию от исходного состояния |
| Команда с `-m` не запускает собственный тест | Запустить свой файл непосредственно: `docker compose run --build --rm tests python -m pytest -q tests/test_my_scenario.py`, заменив имя настоящим |

При вопросе автору укажите этап, команду, состояние контейнеров, версию кода и текст ошибки. Вопросы по заданию принимаются в [Issues](https://github.com/rbeketov/redis-cache-lab/issues/new).

После работы:

```sh
docker compose down
```

Команда удаляет контейнеры и сеть данного учебного проекта. Файлы кода на компьютере сохраняются, демонстрационные данные в памяти исчезают.

Точную дату и время сдачи автор объявляет после согласования с преподавателем. Ориентир 14–16 календарных дней из правил курса не заменяет установленный дедлайн и отличается от трудоёмкости в часах.
